   requirements. A GPU port must preserve portability, CPU performance,
   validated answers, and shared development. Production CPU runs cannot

.. container:: notes

   [2:00–2:30] The branches connect the physical domain to three useful
   computational views; they do not depict a sequence of model operations.
   We classify its computations by dependency, not by the physical equation.
   Layered work offers horizontal concurrency and sometimes concurrency across
   layers. A column solve has horizontal independence but ordered work down
   each column. Mixed solvers combine these patterns: pressure depends on
   overlying layers, and the barotropic mode couples a two-dimensional solve
   to vertically integrated state. The slice illustrates a useful mixed-work
   loop pattern, not every phase of every mixed solver. The diagrams come from
   the GTC poster: orange highlights an independent column; teal highlights
   a layer or an i-k slice. Arrows indicate traversal/depth, not prescribed
   GPU thread geometry. Layer work can also be concurrent in k when there is
   no vertical dependence. This taxonomy tells us how to expose work; later
   we will see why it does not predict speedup by itself.


Fortran describes independent work
==================================

.. container:: loop-pattern

   .. container:: loop-pattern-figure

      .. image:: img/loop_points.svg
         :alt: A fully filled ocean grid with alternating checkerboard cell colors; i, j, and k are all concurrent.

   .. container:: loop-pattern-code

      **Independent grid points**

      .. code:: fortran

         do concurrent (k=1:nk, j=1:nj, i=1:ni)
           a(i,j,k) = b(i,j,k) + c(i,j,k)
         enddo

      Every ``(i,j,k)`` iteration is independent.

``do concurrent`` does not itself require GPU execution.

.. container:: notes

   [2:30–3:10] The loop is standard Fortran, not a GPU-specific directive.
   It states that these iterations may execute in any order. The compiler and
   build configuration decide how to execute them. NVIDIA maps these loops
   through its OpenACC machinery; other vendors have their own implementations.
   The source expresses the algorithmic independence while the compiler chooses
   launch details. But this is not a complete accelerator programming model:
   Fortran does not prescribe host-device transfers, and procedure calls and
   temporary storage still affect whether a useful kernel can be generated.


Independent columns, ordered depth
========================================

.. container:: loop-pattern

   .. container:: loop-pattern-figure

      .. image:: img/loop_columns.svg
         :alt: Colored vertical columns computed independently, with downward arrows showing ordered work in k within each column.

   .. container:: loop-pattern-code

      **One ordered solve per column**

      .. code:: fortran

         do concurrent (j=1:nj, i=1:ni)
           do k=1,nk
             ! Ordered column solve
           enddo
         enddo

      Columns are independent; depth is not.

      Each column keeps its own vertical ordering.

.. container:: notes

   [3:10–3:50] The unit of independent work is now a whole water column,
   not an individual grid point. The outer concurrent loop exposes i-j
   independence; the ordinary k loop retains the vertical dependencies of a
   column solve. Repeated muted colors distinguish columns without assigning
   a distracting unique color to every one. The downward arrows represent
   ordered work, not data movement or a prescribed GPU thread layout.
   This code is a schematic pattern, not an extracted full solver.
   Real column solvers can require private work arrays and an OpenMP fallback.


Concurrent slices, ordered integration
========================================

.. container:: loop-pattern

   .. container:: loop-pattern-figure

      .. image:: img/loop_slices.svg
         :alt: A highlighted i-k slab colored by horizontal row: each i row is concurrent, with downward arrows showing ordered k integration; j selects independent slices.

   .. container:: loop-pattern-code

      **Parallel columns within each slice**

      .. code:: fortran

         do concurrent (j=1:nj)
           do k=1,nk
             do concurrent (i=1:ni)
               s(i,j) = s(i,j) + u(i,j,k)
             enddo
           enddo
         enddo

      Concurrent ``j`` slices and ``i`` columns;
      serial accumulation in ``k``.

.. container:: notes

   [3:50–4:30] Flattening this into one concurrent loop would be wrong:
   each column's accumulation must retain its validated vertical order.
   Different j slices are independent, and within each slice the i loop
   updates independent columns side by side. This j-k-i traversal preserves
   the contiguous i dimension useful to CPU execution. The column and slice
   versions expose related horizontal independence but organize the ordered
   vertical work differently. For this pattern NVIDIA can choose 32 by 4
   thread blocks; that is a compiler choice, not a Fortran guarantee.
   The sketch shows computational dependencies, not CUDA launch geometry.


Blocking reconciles CPU and GPU
===============================

.. image:: img/block_regions.svg
   :width: 90%
   :alt: Matching grid diagrams: a shaded layer on the CPU side represents a cache-friendly part; the entire local domain is shaded on the GPU side to represent a larger kernel work region, not thread geometry or independence in all dimensions.

``do concurrent`` expresses **independence**; the GPU compiler forms **kernels**.

Blocking chooses the work region — same solver, different extents.

.. container:: notes

   [4:30–5:30] Distinguish concurrency from a kernel. Fortran do concurrent
   describes independent iterations, not a GPU launch. In our GPU compilation
   path these loops also delimit work the compiler turns into kernels; the
   exact mapping and kernel formation are compiler decisions, not Fortran
   guarantees. We therefore introduce a computational blocking layer to
   choose how much work is presented at once. On CPUs we select cache-friendly
   parts, illustrated by a layer on the left. On GPUs we expose a larger work
   region, illustrated by the whole local domain on the right, and let the
   compiler map its independent iterations onto GPU threads and thread blocks.
   Shading denotes the work region, not concurrency in every dimension:
   ordered k work can remain serial inside the kernel. The picture is an
   illustrative contrast, not a requirement to launch the entire domain or
   a claim that GPU hardware solves algorithmic dependencies. Computational
   blocks also bound temporary storage and keep control flow outside compact
   kernels. Runtime extents preserve the same solver and module API; these
   algorithmic tiles are distinct from CUDA thread blocks.


Traverse blocks, launch local kernels
==================================================

.. container:: loop-pattern block-traversal

   .. container:: loop-pattern-figure

      .. raw:: html

         <object type="image/svg+xml" data="img/block_loop_title.svg"
           aria-label="Animated traversal of a 26 by 26 domain in 8 by 4 tiles, clipped at the right and bottom edges">
           <img src="img/block_shapes.svg" alt="Computational block shapes">
         </object>

   .. container:: loop-pattern-code

      .. code:: fortran

         do jsb=js,je,njj ; do isb=is,ie,nii
           jeb = min(je, jsb+njj-1)
           ieb = min(ie, isb+nii-1)
           iie = ieb - isb + 1
           jje = jeb - jsb + 1

           do concurrent (jj=1:jje, ii=1:iie)
             i = isb + ii - 1
             j = jsb + jj - 1
             ! Work on this block
           enddo
         enddo ; enddo

The blue boundary shows each GPU kernel.  The CPU steps through each block.

.. container:: notes

   [5:30–6:00] The animation makes the two levels concrete. Ordinary outer
   loops choose an 8 by 4 tile in this illustrative 26 by 26 domain. The
   right edge has 2 by 4 tail tiles, the bottom has 8 by 2 tiles, and the
   final corner is 2 by 2: min clips the bounds rather than padding the grid.
   Within each tile we reconstruct global indices from block-local indices and run
   compact kernels. The moving point illustrates index coverage, not serial
   GPU execution: do concurrent iterations need not follow this scan order.
   This is computational tiling, not a prescribed GPU thread-block shape.
   The code is a shortened pattern from MOM_full_convection.F90: serial
   jsb/isb loops choose each block, min clips its bounds at the domain edge,
   and iie/jje set the local extents. ii/jj index block-sized arrays, while
   i/j address full-domain fields. The actual physics and locality macros
   are omitted here; this is not the complete convection solver. The same
   outer-loop structure appears in several other MOM6 modules.
   Do not wait for the entire animation cycle.

Keep the data on the device
===========================

Fortran has no host/device model. **OpenMP manages transfers.**

.. image:: img/device_residency.svg
   :height: 410px
   :alt: Tall host and device boxes with straight horizontal arrows, ordered top to bottom as OpenMP input copy, two do concurrent launches, an ellipsis, another do concurrent launch, and OpenMP results returned to the host. Device fields remain resident.

We rely on **OpenMP–do concurrent interoperability**.

.. container:: notes

   [6:45–7:45] So far we have deliberately left out data movement. Exposing
   independent work and choosing useful blocks is not enough if every kernel
   copies its fields back and forth. Standard Fortran has no notion of
   host and device, and thus no means to explicitly control transfers
   between them. Leaving that distinction outside the language is a
   reasonable design choice, but we must supply this missing piece.
   We use OpenMP target enter data and target exit data to
   manage the lifetime shown here. Inputs use map(to: b, c), output storage
   uses map(alloc: a), and exit uses map(from: a) and map(delete: b, c).
   Intermediate host access, when needed, can use target update without
   ending residency. Solid gold arrows show data transfers; dashed white
   arrows show successive kernel launches, not copies of resident fields.
   Real model timesteps contain thousands of kernels, so those transfers
   would be devastating. Persistent fields are mapped during initialization
   and retained on the GPU. Modules manage their own temporary storage.
   The significant design decision is mixing OpenMP data management with
   do concurrent kernels lowered through OpenACC in this toolchain.
   Those kernels must resolve OpenMP-managed arrays to the same resident
   device allocations. This interoperability is an explicit toolchain
   requirement, not a guarantee of Fortran or a portable assumption about
   arbitrary OpenMP and OpenACC implementations. The persistent fields
   remain resident across kernels and timesteps.
   Derived types require care as well: mapping the object and its array
   components is one coordinated lifetime problem.

The resident model extends across GPUs
======================================

.. image:: img/dycore_speedup.svg
   :height: 450px
   :alt: Fixed-domain speedup versus H100 GPU count for 256 by 256, 512 by 512, and 1024 by 1024 domains, with an ideal-scaling reference.

Up to **6.1× on 10 H100s**, relative to one H100.

.. container:: notes

   [11:00–12:15] This reproduces the manuscript's fixed-domain strong-scaling
   view using H100s rather than the GH200 of the single-device comparison.
   The horizontal axis is GPU count; each curve fixes the global domain.
   Speedup is relative to one H100 for that same domain. The dashed line
   denotes ideal scaling. Two GPUs
   per node, up to five nodes. FMS packs and unpacks resident halo buffers on
   the GPU and passes device pointers to GPU-aware MPI. The largest domain
   reaches about 6.1 times speedup at ten GPUs; the smallest reaches only
   about 1.4 times as local work shrinks and communication dominates. Importantly,
   GPU-aware MPI does not imply a direct GPU transport: this system lacks
   NVLink and GPUDirect RDMA, and communication is staged through host memory
   and PCIe over NDR-200 InfiniBand. The result demonstrates the distributed
   data-resident implementation, not ideal scaling or a hardware-independent
   communication limit. Rank/device selection uses an OpenACC runtime call in
   the NVIDIA implementation.

   [12:15–13:15] Return to the requirements from the opening: we achieved
   bitwise CPU/GPU agreement in the three tested configurations.
   This required
   preserving arithmetic order, including ordered k accumulations and
   reproducible reductions such as reproducing_sum, using reproducible math
   such as exp_repro rather
   than relying on different CPU/GPU implementations of exp, and controlling
   compiler transformations such as FMA contraction.
   The FMA panel shows source parentheses and possible compiler lowering,
   not explicit fma calls in MOM6. On the GPU toolchain, parentheses do not
   provide the required control over contraction, so GPU FMA contraction
   is disabled. On supported CPU builds, source grouping controls which
   product is rounded separately.
   Preserving accumulation order is why some earlier examples kept k serial;
   independent k work can still be concurrent.
   Bitwise matching is scoped to the tested configurations, toolchain,
   hardware, flags, and run lengths, not universal agreement across vendors
   or optimization settings. The double gyre validates the measured dynamic
   core; two production-style configurations broaden coverage but are still
   partial ports. GPU builds use NVIDIA HPC SDK 26.3. The arithmetic example
   illustrates that reassociation can change floating-point results, not
   that the two expressions always differ.
   The grouping, integer-bin, and FMA diagrams are adapted from the GTC 2026
   poster as native HTML and SVG. The reduction diagram summarizes the
   mechanism: distribute floating-point values into fixed-point integer
   bins, then accumulate without dependence on reduction order. The
   three-bin example is schematic; bin widths, normalization, and overflow handling are
   implementation details omitted from the slide.

   to obtain the same bits, without depicting the approximation's internals.
   For input 1, the displayed binary64 value was checked by compiling the
   local MOM6 exp_repro implementation with gfortran, default real promoted
   to 64 bits, unsafe math disabled, and FMA contraction off. It matches
   the test constant 2.7182818284590452: bits 0x4005BF0A8B145769.
   This local check ran on CPU; the CPU/GPU agreement claim above comes
   from the tested model configurations.


Independence is not enough
==========================

.. image:: img/portability_tradeoff.svg
   :height: 475px
   :alt: Continuity correction changes from layer-wise worksharing to a column per thread. On a 512 by 512 by 100 grid, CPU time grows from 71 to 116 ms, H200 time falls from 49 to 26 ms, and one MI250X GCD falls from 1048 to 103 ms. Different compiler mappings produce a portability tradeoff.

Standard Fortran exposes the work; compilers determine the mapping.

.. container:: notes

   [13:15–14:00] One closing example of the gap between independence and an
   efficient mapping. This is the separate SCA27 continuity-correction study,
   not the GH200/EPYC benchmark. Layer-wise vertical sums keep i contiguous
   and k ordered, but require repeated worksharing within a Newton iteration.
   The column-wise form gives each horizontal face to a thread, which runs
   its own Newton solve and serial k loops and can stop when that face
   converges. This is more than a simple loop interchange: convergence control
   and private iteration state change too. Both forms keep each vertical sum
   ordered. The colored rows and columns depict solver structure, not a
   guaranteed team or warp mapping.
   At 512 by 512 with 100 layers, the rewrite makes this component about 1.6
   times slower on the 104-core Intel Xeon node, 1.9 times faster on H200,
   and 10.2 times faster on one MI250X GCD. AMD benefits especially because
   amdflang's layer-wise lowering incurs repeated generic-mode worksharing
   overhead; the column form uses SPMD lowering. The difference reflects source,
   compiler, runtime, and hardware, not a controlled hardware ranking.
   The AMD component uses a separate explicit-OpenMP source; it is not a
   full AMD dynamic-core port or evidence that unchanged do concurrent works
   equally well everywhere. Standard Fortran takes us far, but expressing
   independence alone does not guarantee an efficient mapping with today's
   compilers. The vertical subslide retains the detailed limitations.
   Source: Yang et al., SCA27 manuscript, section 5.3 and figure 4. Values are
   per-rank mean clock times per dynamics step, taking the fastest of five
   repeats separately for each platform/form. The local CSV retains all five
   samples from the source logs. Do not mix these times with WACCPD timings.


Standards-based, not limitation-free
------------------------------------

.. list-table::
   :widths: 32 68

   * - **Private work arrays**
     - OpenMP target-loop fallback for column solvers
   * - **Procedure calls**
     - Inlining and register pressure matter
   * - **Objects / descriptors**
     - Host-side dispatch; careful component lifetimes
   * - **Runtime control**
     - NVIDIA device selection uses OpenACC; async is outside Fortran
   * - **AMD execution**
     - Selected solvers run on one MI250X GCD

AMD: experimental OpenMP source, not yet a complete dynamic-core port.

.. container:: notes

   Optional detail, outside the main timing budget. The approach is pragmatic:
   do concurrent is the primary
   notation, but current compiler limitations require fallbacks. Vertical
   friction uses OpenMP where private local arrays are not reliably supported.
   Some procedures were manually inlined for this compiler release. Objects
   remain useful on the host, but device kernels prefer statically resolved
   calls and explicit array state. Asynchronous execution is a future
   opportunity, not a measured feature here. We have also run selected MOM6
   components on AMD: vertical viscosity, barotropic stepping, and continuity
   correction. The SCA27 study uses one MI250X GCD (one of the GPU's two compute
   dies), not a full MI250X, on grids up to 512 by 512 with 100 layers. These
   are experimental ports in a separate source using explicit OpenMP target
   teams distribute parallel do, not evidence that the unchanged do concurrent
   source or the complete dynamic core runs on AMD. amdflang's offload lowering
   and support vary across compiler releases. Keep this as evidence of AMD
   execution and compiler investigation, not a cross-vendor hardware ranking
   or a claim of end-to-end AMD performance parity. The headline GH200/H100
   timings in this talk remain separate NVIDIA experiments.
   Source: Yang et al., Fortran Standard Parallelism and OpenMP on NVIDIA and
   AMD GPUs: Cross-Architecture Tradeoffs in MOM6, SCA27 manuscript,
   sections 4.3–4.4 and 5. Local reference: gtc2026/SCA27_paper.pdf; logs and
   plotting provenance: SCA27-paper-data/README.md. No timing data from that
   study are merged into this talk's WACCPD comparisons.


One codebase, solver-aware acceleration
=======================================

**Express** independence with standard Fortran.

**Manage** residency and communication explicitly.

**Preserve** ordering, validated answers, and the CPU path.

**0.396 s/step** on one GH200 at **1024 × 1024 × 100**;
**6.1×** fixed-domain speedup on ten GPUs in the largest test.

Next: diagnostics, parameterizations, and coupled configurations.

.. container:: notes

   [14:00–14:30] The main conclusion is that production-model acceleration
   is not a single-loop transformation. Standard Fortran supplies the central
   expression of concurrency, but residency, ordered work, blocking, compiler
   behavior, and validation make the whole model viable. The dynamic core
   demonstrates acceleration without maintaining a second solver source.

Backup: representative block kernel
--------------------------------------------------

.. code:: fortran

   do jsb=js,je,njj ; do isb=is,ie,nii
     ieb = min(isb + nii - 1, ie)
     jeb = min(jsb + njj - 1, je)
     iie = ieb - isb + 1
     jje = jeb - jsb + 1

     do concurrent (k=1:nz, jj=1:jje, ii=1:iie)
       i = isb + ii - 1
       j = jsb + jj - 1
       visc_rem(ii,jj,k) = visc_rem_u(i,j,k)
     enddo
   enddo ; enddo

Clip edge tiles; use local work arrays and global field indices.

.. container:: notes

   Backup only. This is the representative continuity block kernel from the
   manuscript and September developer talk, not an entire solver. nii and
   njj are configured tile extents; iie and jje are the clipped extents of
   this tile. ii and jj index temporary, block-local arrays. i and j address
   the full-domain fields. The serial outer traversal is deliberately kept
   separate from the compact concurrent kernel. The developer talk also
   distinguishes center and face bounds; Fortran is case-insensitive, so
   capitalization alone does not create distinct variable names.

Backup: derived-type lifetimes
------------------------------

.. code:: fortran

   !$omp target enter data map(to: CS)
   !$omp target enter data map(to: CS%u, CS%v)

   ! Later host-side changes need coordinated updates.
   ! Blindly updating CS can overwrite device references:
   !$omp target update to(CS)

Treat object and component mappings as one residency problem.

.. container:: notes

   Backup only. The final line illustrates a hazard, not a recommended
   operation. Initial mappings are compact; subsequent updates can overwrite
   device-side descriptors or pointers. Object lifetimes, component allocation,
   and host updates must be coordinated. Exact behavior and safe update patterns
   depend on the compiler and the derived type's definition.
