======================================
Performance-portable MOM6 on GPUs
======================================

:subtitle: Standard Fortran and OpenMP
:authors:
   - Marshall Ward
   - Edward Yang
   - Jorge Gálvez Vallejo
   - Utheri Wagura
:description: A solver-aware, single-codebase GPU port of the MOM6 dynamic core.
:kicker: WACCPD 2026
:preface:
   [0:00–0:30] Our question is whether a long-lived community ocean model can
   gain GPU acceleration without a separate implementation or changes to its
   validated answers. We use standard Fortran to express the parallel work and
   OpenMP to keep its data on the device. This talk focuses on the dynamic core,
   not a completed port of the entire production model.

.. container:: notes

   [0:30–1:15] MOM6 is the Modular Ocean Model, an open-source community ocean
   model used for regional and global simulations, forecasting, and climate
   research. The image, reused from the GTC poster, shows Gulf Stream and
   eddy structure in a 5 km Northwest Atlantic configuration. It illustrates
   the scientific application, not the GPU timing benchmark or a claim that
   this particular configuration is operationally deployed or GPU-validated.
   The model supports both ongoing research and operational applications:
   it is not a disposable benchmark kernel. A replacement GPU implementation
   would create a second code to maintain and validate. Changing answers is
   also disruptive: we need to
   distinguish scientific changes from porting errors. CPU execution remains
   important, so a successful port must preserve that path and its performance.
   The approach is deliberately incremental, retaining the model's development
   practices rather than introducing a new language or framework.

.. container:: notes

   [2:00–2:30] The branches connect the physical domain to three useful
   computational views; they do not depict a sequence of model operations.
   We classify its computations by dependency, not by the physical equation.
   Layered work offers horizontal concurrency and sometimes concurrency across
   layers. A column solve has horizontal independence but ordered work down
   each column. Mixed solvers combine these patterns: pressure depends on
   overlying layers, and the barotropic mode couples a two-dimensional solve
   to vertically integrated state. The slice illustrates a useful mixed-work
   loop pattern, not every phase of every mixed solver. The diagrams come from
   the GTC poster: orange highlights an independent column; teal highlights
   a layer or an i-k slice. Arrows indicate traversal/depth, not prescribed
   GPU thread geometry. Layer work can also be concurrent in k when there is
   no vertical dependence. This taxonomy tells us how to expose work; later
   we will see why it does not predict speedup by itself.


Fortran describes independent work
==================================

.. code:: fortran

   do concurrent (k=1:nk, j=1:nj, i=1:ni)
     a(i,j,k) = b(i,j,k) + c(i,j,k)
   enddo

**Source:** iteration independence

**Compiler:** CPU execution or GPU kernel mapping

**OpenMP:** device-data residency

``do concurrent`` does not itself require GPU execution.

.. container:: notes

   [2:30–3:30] The loop is standard Fortran, not a GPU-specific directive.
   It states that these iterations may execute in any order. The compiler and
   build configuration decide how to execute them. NVIDIA maps these loops
   through its OpenACC machinery; other vendors have their own implementations.
   The source expresses the algorithmic independence while the compiler chooses
   launch details. But this is not a complete accelerator programming model:
   Fortran does not prescribe host-device transfers, and procedure calls and
   temporary storage still affect whether a useful kernel can be generated.


Keep the data on the device
===========================

.. code:: fortran

   ! Establish residency
   !$omp target enter data map(alloc: a) map(to: b, c)

   do concurrent (k=1:nk, j=1:nj, i=1:ni)
     a(i,j,k) = b(i,j,k) + c(i,j,k)
   enddo

   ! Return the result when needed
   !$omp target exit data map(from: a) map(delete: b, c)

In MOM6, persistent fields stay resident **across kernels**.

.. container:: notes

   [3:30–4:30] This is a compact illustration of the data lifecycle, not a
   prescription to copy fields around every kernel. Real model timesteps
   contain thousands of kernels, so those transfers would be devastating.
   Persistent fields are mapped during initialization and retained on the GPU.
   Modules manage their own temporary storage. OpenMP-managed arrays must be
   visible to kernels generated from do concurrent: interoperability is an
   explicit toolchain requirement. Derived types require care as well: mapping
   the object and its array components is one coordinated lifetime problem.


Parallel horizontally, ordered vertically
=========================================

.. code:: fortran

   do concurrent (j=js:je)
     do k=1,nz
       do concurrent (i=is-1:ie)
         uhbt(i,j) = uhbt(i,j) + uh0(i,j,k)
       enddo
     enddo
   enddo

* Independent horizontal columns
* Ordered vertical accumulation
* CPU-friendly ``j-k-i`` traversal

.. container:: notes

   [4:30–5:30] Flattening everything into one concurrent loop would be wrong
   here. Each horizontal column is independent, but its sum must follow the
   validated vertical order. Nested concurrency expresses that distinction
   without discarding the contiguous i-loop important to CPU execution. For
   this pattern NVIDIA can produce 32 by 4 thread blocks in the horizontal
   plane while keeping the k accumulation serial. That geometry is a compiler
   implementation detail, not a promise of the Fortran standard. Source loop
   hierarchy is both a correctness decision and a performance decision.


Blocking reconciles CPU and GPU
===============================

.. image:: img/block_shapes.svg
   :width: 90%
   :alt: Layer-oriented, column-oriented, and GPU-oriented computational blocks.

CPU: retain locality. GPU: expose larger work units.

Runtime block extents — same solver, same module API.

.. container:: notes

   [5:30–6:30] Nested loops alone do not solve every mapping problem. Larger
   solvers contain multiple phases and helper calls that can obscure the
   useful parallel structure. Explicit computational blocks keep ordinary
   control flow outside compact kernels and bound temporary storage. The same
   source can use smaller or anisotropic blocks for CPU locality and larger
   horizontal blocks for GPU concurrency. These are algorithmic tiles, not
   necessarily CUDA thread blocks. The key is to make execution geometry a
   configuration choice rather than maintain separate solver implementations.
   Wrappers retain the existing module API, so callers such as RK2 do not
   need to know about the decomposition. Ordinary Fortran controls traversal;
   the inner kernel only sees regular, block-local work.

Preserve answers and CPU performance
====================================

**Bitwise validation:** NVIDIA CPU and GPU builds match in three tested
configurations.

* Preserve vertical ordering and reproducible reductions
* Restrict floating-point transformations where required

.. list-table:: CPU regression check: 384 × 256 × 100
   :header-rows: 1
   :widths: 60 40

   * - Codebase
     - Mean time/step
   * - Production baseline
     - 76.51 ms
   * - GPU-enabled, on CPU
     - 74.89 ms

Ten runs each: no regression in this test; mean time **2.1% lower**.

.. container:: notes

   [7:45–8:45] Bitwise matching is scoped to the tested configurations,
   toolchain, hardware, flags, and run lengths. It is not a claim of universal
   agreement across vendors or optimization settings. The double gyre validates
   the measured dynamic core; two production-style configurations broaden
   coverage but are still partial ports. GPU builds use NVIDIA HPC SDK 26.3,
   with selected transformations disabled, including FMA contraction. The
   separate CPU regression experiment compares the two codebases on identical
   hardware, compiler, flags, and resource layout. Ten repetitions each show
   no regression at this representative size. Standard deviations were 0.075
   and 0.064 ms respectively. Do not generalize this one-case result to every
   configuration or confuse it with the cross-hardware performance comparison.

The resident model extends across GPUs
======================================

.. image:: img/dycore_speedup.svg
   :height: 450px
   :alt: Fixed-domain speedup versus H100 GPU count for 256 by 256, 512 by 512, and 1024 by 1024 domains, with an ideal-scaling reference.

Up to **6.1× on 10 H100s**, relative to one H100.

.. container:: notes

   [12:00–13:15] This reproduces the manuscript's fixed-domain strong-scaling
   view using H100s rather than the GH200 of the single-device comparison.
   The horizontal axis is GPU count; each curve fixes the global domain.
   Speedup is relative to one H100 for that same domain. The dashed line
   denotes ideal scaling. Two GPUs
   per node, up to five nodes. FMS packs and unpacks resident halo buffers on
   the GPU and passes device pointers to GPU-aware MPI. The largest domain
   reaches about 6.1 times speedup at ten GPUs; the smallest reaches only
   about 1.4 times as local work shrinks and communication dominates. Importantly,
   GPU-aware MPI does not imply a direct GPU transport: this system lacks
   NVLink and GPUDirect RDMA, and communication is staged through host memory
   and PCIe over NDR-200 InfiniBand. The result demonstrates the distributed
   data-resident implementation, not ideal scaling or a hardware-independent
   communication limit. Rank/device selection uses an OpenACC runtime call in
   the NVIDIA implementation.


Standards-based, not limitation-free
====================================

.. list-table::
   :widths: 32 68

   * - **Private work arrays**
     - OpenMP target-loop fallback for column solvers
   * - **Procedure calls**
     - Inlining and register pressure matter
   * - **Objects / descriptors**
     - Host-side dispatch; careful component lifetimes
   * - **Runtime control**
     - NVIDIA device selection uses OpenACC; async is outside Fortran

Portable source does not yet mean validated performance on every vendor.

.. container:: notes

   [13:15–14:00] The approach is pragmatic: do concurrent is the primary
   notation, but current compiler limitations require fallbacks. Vertical
   friction uses OpenMP where private local arrays are not reliably supported.
   Some procedures were manually inlined for this compiler release. Objects
   remain useful on the host, but device kernels prefer statically resolved
   calls and explicit array state. Asynchronous execution is a future
   opportunity, not a measured feature here. Our portability claim is about a
   standards-based single source strategy; these GPU measurements are NVIDIA
   results, not a completed cross-vendor performance evaluation.


One codebase, solver-aware acceleration
=======================================

**Express** independence with standard Fortran.

**Manage** residency and communication explicitly.

**Preserve** ordering, validated answers, and the CPU path.

Nearly **3×** single-GPU main-loop speedup;
**6.1×** fixed-domain speedup on ten GPUs in the largest test.

Next: diagnostics, parameterizations, and coupled configurations.

.. container:: notes

   [14:00–14:30] The main conclusion is that production-model acceleration
   is not a single-loop transformation. Standard Fortran supplies the central
   expression of concurrency, but residency, ordered work, blocking, compiler
   behavior, and validation make the whole model viable. The dynamic core
   demonstrates acceleration without maintaining a second solver source.
   Extending this to diagnostics and more complex parameterizations is the
   next step toward coupled production configurations. Thank the collaborators
   and invite questions. Planned spoken content is 14 minutes 30 seconds,
   leaving 30 seconds within a 15-minute slot. If questions must fit inside
   the slot, omit the traversal animation and compress the module breakdown.


Backup: representative block kernel
--------------------------------------------------

.. code:: fortran

   do jsb=js,je,njj ; do isb=is,ie,nii
     ieb = min(isb + nii - 1, ie)
     jeb = min(jsb + njj - 1, je)
     iie = ieb - isb + 1
     jje = jeb - jsb + 1

     do concurrent (k=1:nz, jj=1:jje, ii=1:iie)
       i = isb + ii - 1
       j = jsb + jj - 1
       visc_rem(ii,jj,k) = visc_rem_u(i,j,k)
     enddo
   enddo ; enddo

Clip edge tiles; use local work arrays and global field indices.

.. container:: notes

   Backup only. This is the representative continuity block kernel from the
   manuscript and September developer talk, not an entire solver. nii and
   njj are configured tile extents; iie and jje are the clipped extents of
   this tile. ii and jj index temporary, block-local arrays. i and j address
   the full-domain fields. The serial outer traversal is deliberately kept
   separate from the compact concurrent kernel. The developer talk also
   distinguishes center and face bounds; Fortran is case-insensitive, so
   capitalization alone does not create distinct variable names.


Backup: configuration without API changes
--------------------------------------------------

.. code:: fortran

   subroutine CorAdCalc(...)
     nkk = CS%nkblock
     if (nkk == 0) nkk = GV%ke
     call CorAdCalc_block(..., nkk, ...)
   end subroutine CorAdCalc

.. list-table::
   :widths: 64 36

   * - ``CONTINUITY_NIBLOCK / NJBLOCK``
     - Horizontal block extents
   * - ``CONTINUITY_NKBLOCK``
     - Reconstruction layers
   * - ``CORIOLIS_ADV_NKBLOCK``
     - Advection layers
   * - ``HORVISC_NKBLOCK``
     - Viscosity layers

``0`` selects the full local extent in that direction.

.. container:: notes

   Backup only. These are layout parameters shown in the September developer
   talk. The first table row abbreviates two full parameter names:
   CONTINUITY_NIBLOCK and CONTINUITY_NJBLOCK. Wrappers resolve the configured
   extent before calling the block implementation, preserving the existing
   module interface. Callers do not need separate CPU/GPU APIs. The code is
   schematic; ellipses stand for the original argument list.


Backup: device-resident halo exchange
-------------------------------------

.. image:: img/fms_mpi.svg
   :width: 70%
   :alt: FMS halo buffers exchanged through MPI from GPU-resident memory.

GPU packing → device buffers → GPU-aware MPI → GPU unpacking

The transport beneath MPI remains system-dependent.

.. container:: notes

   Backup only. The OpenACC runtime reconciles the device ID used by
   NVIDIA-generated kernels with the MPI rank's assigned device. Device
   pointers can be handed to MPI even when the MPI implementation stages the
   transfer through host memory. This is why GPU-aware and GPU-direct must
   not be used interchangeably.

Backup: derived-type lifetimes
------------------------------

.. code:: fortran

   !$omp target enter data map(to: CS)
   !$omp target enter data map(to: CS%u, CS%v)

   ! Later host-side changes need coordinated updates.
   ! Blindly updating CS can overwrite device references:
   !$omp target update to(CS)

Treat object and component mappings as one residency problem.

.. container:: notes

   Backup only. The final line illustrates a hazard, not a recommended
   operation. Initial mappings are compact; subsequent updates can overwrite
   device-side descriptors or pointers. Object lifetimes, component allocation,
   and host updates must be coordinated. Exact behavior and safe update patterns
   depend on the compiler and the derived type's definition.
